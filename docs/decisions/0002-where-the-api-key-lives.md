# 0002 — กุญแจของสมาชิกอยู่ที่ไหน และล็อกอินด้วยอะไร

- สถานะ: ตกลงแล้ว
- วันที่: 2026-09-08
- เกี่ยวข้องกับ: `packages/shared/src/keystore.ts`, `packages/db/migrations/003_accounts.sql`, ADR 0001

## บริบท

ADR 0001 ตกลงไว้ว่าชั้นความเข้าใจเปิดให้สมาชิกที่ใส่ API key ของตัวเอง และเขียนข้อกำหนดของกุญแจไว้ว่า
"เก็บใน session ฝั่งเซิร์ฟเวอร์แบบเข้ารหัส มีวันหมดอายุ ไม่ลงดิสก์ ไม่ลง log ไม่ส่งกลับไปหน้าบ้าน"
รุ่น v0.5.0 เป็นรุ่นที่ต้องทำสิ่งนี้ให้เกิดขึ้นจริง จึงต้องตอบสองคำถามที่ ADR 0001 เว้นไว้
คือจะยืนยันตัวตนด้วยวิธีไหน และกุญแจจะไปอยู่ที่ไหนกันแน่

## การตัดสินใจ

### หนึ่ง — ล็อกอินด้วยบัญชีในระบบเอง

อีเมลกับรหัสผ่าน เก็บใน Postgres แฮชด้วย scrypt (N=2^15) พร้อมเกลือของตัวเองต่อหนึ่งรหัสผ่าน
session เป็นโทเค็นสุ่ม 256 บิตในคุกกี้ `HttpOnly; SameSite=Lax` และฐานข้อมูลเก็บเฉพาะค่าที่ย่อด้วย SHA-256

เลือกทางนี้เพราะทั้งระบบมีวินัยข้อหนึ่งว่าทดสอบใน Docker เท่านั้นและ CI ต้องเขียวทุกครั้ง
วิธีที่ต้องพึ่งบริการภายนอก — OAuth ของ GitHub หรืออีเมลลิงก์เข้าใช้ — ทดสอบครบวงจรไม่ได้
โดยไม่สร้างของปลอมขึ้นมาแทน ซึ่งแปลว่าเส้นทางที่ผู้ใช้เดินจริงจะไม่เคยถูกทดสอบเลย

### สอง — กุญแจอยู่ใน Redis เท่านั้น ไม่ลง Postgres

ตาราง `users` และ `sessions` ไม่มีคอลัมน์สำหรับกุญแจ และตั้งใจให้ไม่มีตลอดไป
กุญแจถูกเข้ารหัสด้วย AES-256-GCM โดยใช้ `SESSION_SECRET` แล้วเก็บใน Redis ที่คีย์ `apikey:<session>`
พร้อมอายุ 12 ชั่วโมง สั้นกว่าตัว session ที่อยู่ได้ 30 วันมาก

Redis ถูกตั้งให้ทำงานในหน่วยความจำล้วน (`--save '' --appendonly no`) ทั้งสามสภาพแวดล้อม
เพราะถ้าเปิดการเขียนลงดิสก์ไว้ ข้อความว่า "ไม่ลงดิสก์" จะเป็นเพียงความตั้งใจ ไม่ใช่สิ่งที่เป็นจริง

## ผลที่ตามมา

- สำเนาสำรองของฐานข้อมูลไม่มีวันมีกุญแจของใครติดไปด้วย เพราะกุญแจไม่เคยผ่านเข้าไปที่นั่น
- กุญแจผูกกับ session ไม่ใช่กับบัญชี การเข้าใช้จากเครื่องใหม่จึงต้องใส่กุญแจใหม่
  ซึ่งเป็นผลที่ต้องการ — เครื่องที่ยืมคนอื่นมาใช้ไม่ควรเรียกใช้โมเดลด้วยเงินของเจ้าของบัญชีได้ตลอดไป
- รีสตาร์ต Redis แล้วกุญแจที่ผูกไว้และงานที่ค้างคิวจะหาย ผู้ใช้ต้องใส่กุญแจใหม่และสั่งงานใหม่
  แลกกับการที่ความลับไม่มีทางตกค้างอยู่บนดิสก์ ถือว่าคุ้ม เพราะการรีสตาร์ตเกิดไม่บ่อย
  และงานวิเคราะห์สั่งซ้ำได้โดยไม่เสียอะไร
- `SESSION_SECRET` กลายเป็นความลับที่สำคัญที่สุดของระบบ ถ้าค่านี้เปลี่ยน กุญแจที่ผูกไว้ทั้งหมดถอดไม่ออก
  ระบบจะทิ้งของที่ถอดไม่ออกแล้วให้ผู้ใช้ใส่ใหม่ แทนที่จะปล่อยให้ค้างอยู่แบบใช้การไม่ได้
- API ปฏิเสธที่จะเปิดบริการบนเซิร์ฟเวอร์จริงถ้าไม่มี `SESSION_SECRET`
  ล้มตั้งแต่ตอนเปิดเครื่องดีกว่าเข้ารหัสความลับของผู้ใช้ด้วยค่าที่ใคร ๆ ก็เดาได้

## ทางเลือกที่ไม่เลือก

- **GitHub OAuth** — เข้ากับตัวโปรเจกต์ที่สุดและต่อยอดไปอ่าน repo ส่วนตัวได้ในอนาคต
  แต่ต้องมี OAuth App จริงตั้งแต่วันแรก และทดสอบใน Docker แบบปิดเน็ตไม่ได้
  ยังเป็นทางที่เปิดไว้สำหรับรุ่นหลัง โดยเพิ่มเป็นวิธีล็อกอินอีกทางหนึ่งบนตารางผู้ใช้เดิม
- **อีเมล + ลิงก์เข้าใช้** — ไม่มีรหัสผ่านให้หลุด แต่ต้องมี SMTP จริงจึงจะใช้งานได้
  และเวลาไม่มี SMTP ก็ต้องทำตัวส่งเมลปลอมไว้ตอนพัฒนา ซึ่งกลายเป็นโค้ดที่ต้องดูแลโดยไม่มีใครใช้จริง
- **เก็บกุญแจใน Postgres แบบเข้ารหัส** — ทนต่อการรีสตาร์ตมากกว่า
  แต่ขัดกับข้อกำหนดของ ADR 0001 ตรง ๆ และทำให้ความลับของผู้ใช้ไปโผล่ในสำเนาสำรองทุกชุด
- **ให้ผู้ใช้ใส่กุญแจใหม่ทุกครั้งที่สั่งสรุปโดยไม่เก็บเลย** — ปลอดภัยที่สุดแต่ใช้งานจริงไม่ไหว
  เพราะงานสรุปทำงานเบื้องหลังเป็นนาที และผู้ใช้ปิดหน้าเว็บไปแล้วงานต้องไปต่อได้
