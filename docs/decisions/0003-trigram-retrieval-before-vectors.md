# 0003 — ค้นคืนบริบทด้วย pg_trgm ก่อนลงทุนกับเวกเตอร์

- สถานะ: ตกลงแล้ว
- วันที่: 2026-09-08
- เกี่ยวข้องกับ: `packages/db/src/search.ts`, `packages/db/migrations/005_search.sql`, PLAN.md ข้อ 5

## บริบท

PLAN.md วางสถาปัตยกรรมไว้ตั้งแต่ v0.1.0 ว่าจะใช้ pgvector + โมเดลฝังเวกเตอร์ bge-m3 บน ONNX Runtime
สำหรับค้นคืนบริบทให้ชั้นถาม–ตอบของ v0.6.0 แต่ตอนถึงเวลาทำจริง คำถามที่ต้องตอบคือค้น "ชื่อไฟล์"
"ชื่อฟังก์ชัน" และ "หัวข้อสรุปที่มีอยู่แล้ว" — ข้อความสั้นที่มักมีคำหรือส่วนของคำตรงกับคำถามอยู่แล้ว
ไม่ใช่ประโยคยาวที่ต้องเข้าใจความหมายเชิงลึกเพื่อจับคู่แบบที่การค้นเชิงความหมายแก้ปัญหาได้ดีกว่า

## การตัดสินใจ

ใช้ `pg_trgm` ของ Postgres แทนเวกเตอร์ฝังในรุ่นนี้

- เพิ่ม extension `pg_trgm` และดัชนี GIN บน `symbols.name` กับ `files.path`
- ค้นข้อความสรุปที่ทำไว้แล้วจากชั้นความเข้าใจของ v0.5.0 (`summaries.points`) ด้วย `similarity()` เช่นกัน
- รวมผลจากสามแหล่งนี้เป็นหลักฐานส่งให้โมเดลสังเคราะห์คำตอบ โดยโมเดลเห็นเฉพาะหลักฐานที่ค้นมาให้เท่านั้น
  ไม่กลับไปโคลนซอร์สใหม่ทุกครั้งที่มีคนถาม เพราะช้าเกินกว่าจะเป็นบทสนทนาที่ตอบสนองทันที

## ผลที่ตามมา

- ไม่ต้องเพิ่มคอนเทนเนอร์รันโมเดลฝังเวกเตอร์ ไม่ต้องดูแลเวอร์ชันโมเดลแยกจากตัวหลัก
  และ `pg_trgm` มากับอิมเมจ `postgres:17-alpine` อยู่แล้ว ไม่มี dependency ใหม่ให้ต้องไว้ใจเพิ่ม
- ค้นได้แม่นเมื่อคำถามมีคำที่ตรงหรือใกล้เคียงกับชื่อไฟล์/ฟังก์ชัน/หัวข้อสรุปจริง
  แต่ค้นคำถามเชิงแนวคิดที่ไม่มีคำตรงกับโค้ดเลย (เช่น "ส่วนที่ทำให้ระบบช้า" โดยไม่มีไฟล์ชื่อ "slow")
  จะไม่เจอ — คำตอบในกรณีนั้นคือระบบต้องบอกตรง ๆ ว่าหาหลักฐานที่ตรงคำถามไม่เจอ ไม่ใช่เดา
- คำตอบผูกกับสิ่งที่ค้นเจอในฐานข้อมูลเท่านั้น ไม่ใช่ซอร์สทั้ง repo แบบสด ๆ
  ถ้าผู้ใช้ยังไม่เคยสั่งสรุป repo ด้วย AI คำตอบจะอาศัยได้แค่ชื่อไฟล์กับชื่อฟังก์ชัน ไม่มีคำอธิบายเชิงเนื้อหา
  ให้ค้นเจอ — คุณภาพคำตอบจึงดีขึ้นเองเมื่อผู้ใช้สั่งสรุป repo ไว้ก่อนแล้ว
- ยังทิ้งช่องไว้ให้เพิ่มเวกเตอร์ฝังทีหลังได้โดยไม่ต้องรื้อของเดิม — ตาราง `summaries` และ `symbols`
  ที่มีอยู่แล้วเป็นแหล่งข้อมูลตั้งต้นที่พร้อมนำไปฝังเป็นเวกเตอร์ในรุ่นถัดไปถ้าพบว่า `pg_trgm` ไม่พอ

## ทางเลือกที่ไม่เลือก (ในรุ่นนี้)

- **pgvector + bge-m3 ตาม PLAN เดิม** — ค้นเชิงความหมายได้กว้างกว่า ตอบคำถามที่ไม่มีคำตรงกับโค้ดได้
  แต่ต้องเพิ่มคอนเทนเนอร์รันโมเดล ONNX แยก เพิ่มเวลา build และความซับซ้อนของ pipeline การวิเคราะห์
  (ต้องฝังเวกเตอร์ทุกไฟล์ทุกครั้งที่วิเคราะห์) ทั้งที่ยังไม่มีหลักฐานว่า `pg_trgm` ไม่พอสำหรับคำถามจริง
- **เก็บซอร์สที่โคลนมาไว้ถาวรเพื่อค้นแบบเต็มข้อความ** — ขัดกับสถาปัตยกรรมที่วางไว้ตั้งแต่ v0.2.0
  ว่าโฟลเดอร์ที่โคลนมาเป็นของชั่วคราว ลบทิ้งทันทีที่วิเคราะห์เสร็จ การเก็บไว้ถาวรเพิ่มพื้นที่ดิสก์
  แบบไม่มีเพดานตามจำนวน repo และเพิ่มความเสี่ยงด้านความปลอดภัยของโค้ดที่ไม่น่าไว้ใจ
