# สถาปัตยกรรม RepoLens

เอกสารนี้อธิบายของที่ "มีอยู่จริงในโค้ดตอนนี้" ส่วนภาพรวมทั้งโครงการและสิ่งที่ยังไม่ได้ทำอยู่ใน [PLAN.md](../PLAN.md)

## สถานะปัจจุบัน: v0.8.0

อ่าน repo ได้ครบทั้งเชิงโครงสร้างและเชิงความหมาย — โคลน อ่านโครงสร้างโค้ด เชื่อมความสัมพันธ์
คำนวณตัวชี้วัด สรุปเป็นภาษาไทยรายไฟล์ รายโมดูล และทั้ง repo แล้วต่อยอดเป็นถาม–ตอบกับ repo
และเส้นทางอ่านโค้ดสำหรับคนใหม่ ทั้งหมดนี้เปิดให้สมาชิกที่ใส่กุญแจของตัวเอง
วิเคราะห์ repo เดิมซ้ำได้เร็วขึ้นด้วยการข้ามไฟล์ที่ไม่เปลี่ยน และมีลิงก์ถาวรที่จำง่ายกว่ารหัสงาน
หน้าเว็บผ่านการตรวจ WCAG 2.1 AA ด้วย axe-core ทุกหน้าหลักทั้งธีมสว่างและมืด และใช้งานได้บนมือถือ

```
เบราว์เซอร์ ──▶ web (Next.js 15, พอร์ต 3000)
                 │  ส่งต่อ /api/* ──▶ api (Fastify 5, พอร์ต 3001)
                 │                       ├─ PostgreSQL 17  (ผลวิเคราะห์)
                 │                       ├─ Redis 7        (คิวงาน + ความคืบหน้า)
                 │                       └─ docs/changelog (บันทึกรุ่น)
                 │                              │
                 │                        คิว BullMQ
                 │                              ▼
                 └─ SSE ◀── ความคืบหน้า ── worker ──▶ git clone ──▶ tree-sitter ──▶ กราฟ
```

หน้าบ้านไม่คุยกับ API โดยตรงจากเบราว์เซอร์ แต่ผ่านตัวส่งต่อที่ `app/api/[...path]/route.ts`
ทำให้ทั้งตอนพัฒนาและตอนขึ้นจริงใช้เส้นทางเดียวกัน และ Caddy มีหน้าที่เดียวคือส่งทุกอย่างไปที่ web

ตัวส่งต่อเป็น route handler ไม่ใช่ `rewrites` ใน `next.config` เพราะ rewrites ถูกคำนวณตอน build
ค่า `API_ORIGIN` จะถูกฝังตายไปกับอิมเมจ (เจอปัญหานี้จริงตอนทดสอบ e2e ของ v0.1.0)
ส่วน route handler อ่านค่าตอนรันจริง และส่งต่อ body แบบสตรีมได้ ซึ่งจำเป็นกับ SSE ของไปป์ไลน์วิเคราะห์

## ทำไมแยก worker ออกจาก API

การโคลนและอ่านโค้ดกินเวลาหลายวินาทีถึงหลายนาที และกินหน่วยความจำเป็นก้อน
ถ้าทำในกระบวนการเดียวกับ API ทุกคำขอของผู้ใช้คนอื่นจะหน่วงตามไปด้วย
คิวยังทำให้ยกเลิก ลองใหม่ และจำกัดจำนวนงานพร้อมกันได้จากที่เดียว

## การอ่านโครงสร้างโค้ด

tree-sitter รุ่น WebAssembly เป็นตัวหลัก เลือกแบบนี้เพราะ binding แบบ native ต้องคอมไพล์ตอนติดตั้ง
ซึ่งทำให้อิมเมจใหญ่และพังง่ายเวลาเปลี่ยนเวอร์ชัน Node
เวอร์ชันของ runtime กับไวยากรณ์ต้องเข้าคู่กัน — `web-tree-sitter` 0.20.8 คู่กับ `tree-sitter-wasms` 0.1.13
ถ้าโหลดไวยากรณ์ไม่ได้ ตัวแยกแบบรูปแบบข้อความจะทำงานแทนและผลลัพธ์จะบอกว่าใช้ตัวไหนไป

## ระดับการใช้งาน

นิยามอยู่ที่ `packages/shared/src/tiers.ts` ที่เดียว ทั้งหน้าบ้านและหลังบ้านอ่านจากตารางนั้น
รายละเอียดการตัดสินใจอยู่ใน [ADR 0001](decisions/0001-two-tier-byok.md)

## ตัวตนและกุญแจของสมาชิก

บัญชีอยู่ใน Postgres — รหัสผ่านแฮชด้วย scrypt และ session เก็บเฉพาะค่าที่ย่อด้วย SHA-256
ส่วน **API key ของสมาชิกไม่เคยลง Postgres** มันอยู่ใน Redis ที่ทำงานในหน่วยความจำล้วน
เข้ารหัสด้วย AES-256-GCM และหมดอายุเองใน 12 ชั่วโมง เหตุผลทั้งหมดอยู่ใน
[ADR 0002](decisions/0002-where-the-api-key-lives.md)

## ชั้นความเข้าใจ

ทำงานแบบ map-reduce สามชั้น: ไฟล์ → โมดูล (ตามโฟลเดอร์) → ทั้ง repo
งานนี้อยู่คนละคิวกับงานวิเคราะห์ เพราะกินเวลาเป็นนาทีและรอเครือข่ายเป็นหลัก

กติกาข้อเดียวที่ทั้งชั้นนี้ยึด: **ข้อความที่ชี้บรรทัดจริงไม่ได้ จะไม่ถูกแสดง**
ตัวตรวจใน `packages/ai/src/grounding.ts` ตัดข้ออ้างอิงที่ไฟล์ไม่มีอยู่หรือบรรทัดเกินขนาดไฟล์ทิ้ง
แล้วตัดข้อความที่ไม่เหลืออ้างอิงออกทั้งข้อ ส่วนไฟล์ที่เกินเพดานการเรียกโมเดล
จะได้คำอธิบายที่ระบบเขียนเองจากโครงสร้าง และติดป้ายว่ามาจากไหน — ไฟล์ทุกไฟล์จึงมีคำอธิบายเสมอ

## ถาม–ตอบกับ repo และเส้นทางอ่านโค้ด

ทำงานเสร็จในคำขอเดียว ไม่เข้าคิวเบื้องหลังเหมือนงานสรุป เพราะเรียกโมเดลแค่ครั้งเดียวต่อคำถาม
หรือต่อการสร้างเส้นทางหนึ่งชุด — สิ่งที่ใช้เวลานานของชั้นความเข้าใจคือการเรียกโมเดลซ้ำเป็นร้อยครั้ง
ต่อไฟล์ ซึ่งทั้งสองฟีเจอร์นี้ไม่มี

**ถาม–ตอบ** ค้นคืนบริบทด้วย `pg_trgm` แทนเวกเตอร์ฝัง (เหตุผลอยู่ใน
[ADR 0003](decisions/0003-trigram-retrieval-before-vectors.md)) จับคู่คำถามกับชื่อไฟล์ ชื่อฟังก์ชัน
และข้อความสรุปที่ทำไว้แล้วจาก v0.5.0 โมเดลเห็นเฉพาะหลักฐานที่ค้นมาให้เท่านั้น ไม่กลับไปโคลนซอร์สใหม่

**เส้นทางอ่านโค้ด** เรียงไฟล์ด้วย topological sort บนกราฟการนำเข้าล้วน ๆ (ใน
`packages/ai/src/reading-path.ts`) ไม่ใช้โมเดลตัดสินลำดับ — ไฟล์ที่ไม่พึ่งพาใครมาก่อน
(โค้ดพื้นฐาน) ไล่ไปจนถึงจุดเริ่มโปรแกรม โมเดลมีหน้าที่แค่อธิบายว่าทำไมแต่ละขั้นถึงควรอ่านตอนนั้น

## วิเคราะห์ซ้ำแบบ incremental

เมื่อสั่งวิเคราะห์ repo ที่เคยวิเคราะห์เสร็จมาก่อน worker จะดึงผลของรอบล่าสุด (ไม่สนคอมมิต)
มาเป็น `previousFiles` ก่อนเริ่ม (`getPreviousSnapshot` ใน `packages/db/src/analyses.ts`)
ไฟล์ที่ค่าแฮชตรงกับรอบก่อนจะไม่ถูกอ่านหรือพาร์สด้วย tree-sitter ซ้ำเลย — ใช้ symbol, เส้นเชื่อม,
ข้อสังเกตด้านความปลอดภัย และแพ็กเกจภายนอกของไฟล์นั้นจากรอบก่อนแทนทั้งหมด

**ข้อจำกัดที่รู้ตัวและยอมรับ:** เส้นเชื่อมของไฟล์ที่ไม่เปลี่ยนจะไม่ถูกคำนวณใหม่ ถ้าการเพิ่ม/ลบไฟล์อื่น
ในรอบนี้ทำให้ import ที่เคย unresolved ของไฟล์นั้นควรจะแก้ได้แล้ว มันจะยัง unresolved ต่อไป
จนกว่าไฟล์นั้นจะถูกแก้เนื้อหาจริงหรือมีคนสั่งวิเคราะห์ใหม่ทั้งหมด ส่วนเส้นที่ชี้ไปไฟล์ที่ถูกลบแล้ว
จะถูกกรองทิ้งเสมอ ไม่มีเส้นลอยค้าง

ไฟล์ที่ใช้ผลเดิมซ้ำยังต้องรวมอยู่ในยอด `engines.treeSitter`/`engines.pattern` ของรอบใหม่ด้วย ไม่ใช่แค่
ไฟล์ที่พาร์สใหม่จริง — ตาราง `files` จึงเก็บคอลัมน์ `engine` ต่อไฟล์ไว้ (v0.8.0) ให้ `getPreviousSnapshot`
ส่งค่านี้กลับไปให้รอบถัดไปรวมยอดต่อได้ แม้ไฟล์นั้นจะไม่ถูกพาร์สใหม่เลยในรอบนั้น

## ลิงก์ถาวร

`/r/[host]/[owner]/[name]` เปิดได้เสมอโดยไม่ต้องจำรหัสงานวิเคราะห์ — หน้านี้ยิง
`POST /api/analyses` ตัวเดียวกับหน้าแรก (ซึ่งดูแคชตาม repo ให้อยู่แล้ว) แล้วพาไปหน้าความคืบหน้า
ที่เชื่อม SSE จริงต่อทันที

## เลขรุ่นสองชุด

- **เวอร์ชันแอป** (`package.json` → `/api/version`) เปลี่ยนทุกครั้งที่ปล่อยของ
- **สคีมาตัววิเคราะห์** (`ANALYZER_SCHEMA` ใน shared) เปลี่ยนเมื่อผลวิเคราะห์รูปแบบเก่าใช้ไม่ได้แล้ว
  ซึ่งแปลว่าต้องล้างแคชผลวิเคราะห์ทั้งหมด — จึงแยกจากเวอร์ชันแอปโดยตั้งใจ
